# Beginner workflow acceptance

This checklist defines evidence needed to accept the guided fee-request workflow. It is not a receipt saying those checks have passed. Prior acceptance is recorded in the [completed foundation plan](assistant/exec_plans/completed/2026-09-30_development_foundation.md). Record new results and limitations in the task's active plan and [current handoff](next-thread-handoff.md), following the [plan lifecycle](assistant/exec_plans/PLANS.md).

Use the final served build, a new isolated synthetic runtime and fictional source fixtures. Default checks strip provider configuration and never use real case history, personal profiles or Gmail IDs. A separately authorized provider acceptance session may pass the existing fee-app key only to that isolated process, bound calls/cost/time, and use fictional documents with `store=False`; record actual usage and failures separately from provider-free checks. Never contact real Gmail for this checklist.

| Step or safeguard | Required observation |
| --- | --- |
| Start | The idle page offers one clear source-upload action. Empty review panels and advanced tools do not distract from that step. |
| Upload | A synthetic notification PDF and a synthetic photo/screenshot enter the same review-first flow. No fee PDF, draft or record is created just by reviewing a source. |
| Recovered facts | The user can see what was found, inspect evidence, and correct it. Missing/uncertain fields stay visibly unresolved rather than acquiring invented values. |
| Numbered answers | Missing questions are prominent. Applying short numbered answers updates the current request and reruns ordinary review. |
| Date confirmation | Without a saved photo-date policy, a capture-date suggestion stays evidence until the service date is confirmed. Unresolved conflicts stop preparation; choosing another date or remaining unsure is possible. |
| Saved photo defaults | In an opted-in isolated runtime, capture day becomes service day and the actual capture city selects its configured court/contact, with visible default labels and editable exceptions. A district header/stale profile/unrelated source footer cannot replace the routing. Missing/competing metadata or absent/ambiguous city-court contacts pause. Unconfigured and non-photo behavior stays covered. |
| Invalid work and duplicates | Translation/word-count sources, missing required information, drafted/sent duplicates and active drafts block the normal creation path with an understandable next action. |
| Ready request | The user reaches the Portuguese draft preview through the visible next-step action. PDF creation still requires the current valid review/preflight. |
| Claim choice | The ordinary review offers interpreting and travel, interpreting only, or travel only. New requests default to both. Interpreting-only does not ask for unused travel data; travel-only describes attendance and requests transport without claiming performed interpreting or adding the saved service-specific tax assertion. No claims selected cannot create a document. |
| Shared visit | A reviewed multi-case source has an explicit, editable shared-trip owner. Only that request claims transport; separate trips and no travel remain available. Moving the owner preserves each case's interpreting choice. Conflicting visit details or an owner with no remaining claim pauses visibly. Check preflight, preparation and synthetic later-record guards against a second travel claim, without collapsing independent visits by city/date. |
| PDF | Open/render the generated synthetic PDF and inspect text, recipient/entity wording, dates, amounts/travel wording and page layout. A successful file write or text assertion alone is insufficient. |
| Recipient choice | Saved contacts populate the recipient picker; ordinary input/change and same-value choices clear stale aliases/overrides. Exact local payer mapping beats broad aliases, ties pause, keyed wrong courts cannot bypass payer checks, and a clear selection resolves irrelevant footer ambiguity. Automatic recovery never picks the first of several contacts. |
| Email target | Source mode groups five requests from one photo into one email with five own PDFs; another photo stays separate, even with the same court/date. Missing hashes remain individual; conflicting recipient/profile selections pause. Separate emails remain available. Review each member's facts and PDF. Handoff/copy/create/record/lifecycle use the frozen group; switching clears per-target acknowledgement and ignores late successes and failures. Packet remains one target. |
| Group correction and recording | A source replacement checks every child against existing history with a correction reason. Every recorded child retains its own PDF/hash. A new sibling duplicate, sent case, incomplete supersedes, changed child PDF/payload or partial replacement that loses sibling protection must block before any provider call or history write. Re-recording the same returned draft identity is idempotent. |
| Manual handoff | The current prepared PDF leads to a handoff packet containing the reviewed recipient/body/attachments. Building/copying it does not contact Gmail or create local draft records. |
| Local recording | Fake draft IDs are accepted only in an isolated test and with current prepared-review binding plus the review acknowledgement. Duplicate protection is updated for every underlying request. |
| Stale state | Editing source/intake/queue/attachments after preparation clears old previews/handoff/record helpers. Reusing stale preparation is rejected by the server too. |
| Reset and connectivity | Reset clears visible client state without removing stored history. A disconnected server visibly blocks server-writing actions. |
| Unfinished-session resume | Edit and queue a five-case source with a nonfirst travel owner and per-case answers, reload, and explicitly resume. The top-of-page controls remain visible at desktop/mobile widths, even when the upload panel is reordered. Inputs/evidence/claims/queue survive; preparation, Gmail IDs and acknowledgements do not. Fresh case review and batch preflight are required. Also exercise source-free manual typing, Change source, Reset, unavailable profiles/files, a delayed resume, storage failure and a different runtime on the same address. Missing conditional answer controls must not interrupt restoration. |
| Backup and machine move | In isolated runtimes, export a pending Gmail attempt and restore it into another runtime. Valid reviewed recovery files must support local-only recording of the same IDs. Newer local history/pending reservations survive older or legacy backups; conflicts pause before replacement. Incomplete or changed files produce visible warnings and keep duplicate blockers. Interrupt restore and retry the same backup without a new remote create. Credentials and unrelated/completed document archives stay excluded. |
| Usability | Main actions remain legible at the reviewed desktop/mobile widths; keyboard focus reaches upload, answer and preview actions without hidden controls trapping it. |

Use focused public tests for the changed behavior, a real browser for the visible sequence, and a rendered PDF for document acceptance. A missing browser/file-input/rendering capability is a recorded limitation, not permission to substitute private data or claim that another kind of check proved the same result.

Run [Full validation](validation.md) on the final integrated build before publication is proposed. Actual real-document/provider use and future main-app integration remain separately scoped acceptance.
